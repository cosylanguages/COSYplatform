# Retrieval plan: general-it-b1

What each lesson should ask the learner to reactivate, computed from the block registry.
Spacing: return at +1, +2, then +4, +8, +12 lessons. Five questions per lesson at most,
resolved blocks and the longest-waiting ones first. This is an input to authoring stage 2,
not a substitute for it: a row here is a block to ask about, the question still has to be written.

- lessons: **65**, blocks: **244**
- scheduled returns: **500**
- hold blocks: **244**, recognise-only: **256**
- lessons at the cap of 8: **58**
- lessons with nothing due: **1**
- blocks introduced too late to return: **1**
- unresolved blocks appearing in the plan: **80** (teachable, but not yet linked to COSYdata)

## Capacity: what 8 questions a lesson can carry

This course introduces **3.8 blocks per lesson**. The method returns each
block five times, so it needs **1168** returns; the schedule has room for
**512** (8 per lesson), which honours **500** and defers
**668**. A course of this length can hold roughly
**102** blocks at this budget.

That gap is not a bug in the planner, it is the arithmetic of the method: the current item load
is more than a retrieval slot of this size can sustain, which is the mechanical reason
a third of the vocabulary is never asked about again. Only hold blocks are scheduled here;
recognise-only blocks are deliberately not returned. The remaining gap has three answers: the
load comes down, the slot grows, or the triage gets stricter.
